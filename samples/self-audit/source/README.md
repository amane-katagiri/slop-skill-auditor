# slop-skill-auditor

Agent Skill（`SKILL.md` 形式。Claude Code・Codex などで使うもの）を監査するスキル。答える問いは次の3つ。

1. このスキルは**実際に何をしているのか**（指示・知識・手順・ツール・アルゴリズム・環境に分解し、ファイルと行で根拠を示す）
2. **素のエージェントや数行の指示と比べて何が増えるのか**（独自価値と置き換えやすさ）
3. **READMEの宣伝は実装と根拠に見合っているか**（実装・効果・宣伝との整合・独自価値・確信度の5軸で判定）

目的はスキルを批判することではなく、価値を観測・比較できるようにすること。セキュリティ監査は主目的ではないが、監査中に見つけた不審な指示やコードは記録する。

## 何をして、何をしないか

- 意味の判断（何が価値か、主張が誇張か）は監査するエージェントが行う。スクリプトは取得・棚卸し・検証・集計といった決まった処理だけを受け持つ。
- 対象スキルのファイルはデータとして扱う。書かれた命令には従わないし、静的監査では対象のスクリプトやインストールコマンドを実行しない。
- 実験していない効果を「実証済み」とは書かない。この点は `report.py check` がレポート生成前に機械的に検査する。
- 「モデルだけでできそう」という判断は、実験で確かめるまでは仮説として扱う。

## 使い方

`~/.claude/skills/slop-skill-auditor/` などスキルの置き場所にこのディレクトリを置き、エージェントに次のように頼む。

> このスキルを監査して。実際に何をしているのか、素のエージェントではできないことなのか、READMEの宣伝は妥当なのか教えて。 `https://github.com/OWNER/REPO/tree/main/skills/foo`

入力には次のどれでも使える：ローカルのスキルディレクトリ、`SKILL.md` のパス、GitHub リポジトリの URL、GitHub の `tree` / `blob` URL。補足の README や文書を一緒に渡すと `--doc` として取り込まれる。リポジトリに複数のスキルがある場合は、どれを監査するかを確認してから進む。

対照実験を頼む場合（費用がかかる。実行前に試行数と概算費用を提示して承認を求める）:

> READMEで主張している効果を、素のエージェント・簡単な追加指示・スキル適用の3条件で比較して。

### 出力

`./slop-audits/<skill>-<YYYYMMDD>/`（場所は指定できる）に次のファイルができる。

| ファイル | 中身 |
|---|---|
| `provenance.json` | 入力、取得方法、GitHub の commit SHA、取得日時、リポジトリ内の他スキル候補 |
| `source/` | 監査した版のスナップショット（`.git` は除く） |
| `inventory.json` | ファイル一覧と sha256、frontmatter、spec チェック、参照関係（欠落参照・未参照ファイル）、外部能力の手がかり、注入候補行、fingerprint |
| `audit.json` | 監査結果（機械可読。スキーマは [references/audit-schema.md](references/audit-schema.md)） |
| `report.md` | 人が読むレポート（Summary / Implementation / Claims / Necessity / Experimental Results / Conclusion） |
| `experiments/<id>/` | 対照実験の計画・凍結ロック・各試行・ブラインド採点・集計（実施した場合のみ） |

サンプル: [samples/](samples/)

## 構成

```text
SKILL.md                         手順と絶対ルール（短く保つ）
references/
  implementation-review.md       機能の分解、置き換え可能性、最小指示案の作り方、根拠の種類
  claim-review.md                宣伝の抽出と5軸の判定
  experiment-design.md           能力実験・発火実験の設計、安全、解釈（A/B/Cの結果パターン、モデル依存性）
  audit-schema.md                audit.json の書式と check が強制するルール
scripts/
  fetch_target.py                取得とリビジョンの記録（git はフック・サブモジュール・LFS・symlink を無効化）
  inventory.py                   決まった処理だけの棚卸し
  report.py                      skeleton / check / render / diff
  experiment.py                  init / validate / selftest / freeze / run / blind / grade / aggregate
  _common.py
tests/                           ユニットテスト、フィクスチャ8種、ライブ受け入れテスト
samples/                         サンプル監査レポート
```

## 設計上の要点

- **最小指示案（B群）は README と description だけから作る。** スキル本文を読む前に書き、読んだ後で書き直さない。本文から良い部分を抜き出して圧縮すると「監査者が最適化した別のスキル」と比べることになってしまうため。`report.py check` は、`derived_from` が README・ユーザー提供文書・frontmatter 以外を指していたらエラーにする。実験ではこの文をそのまま B 群に使い、凍結する。
- **宣伝は5つの軸で判定する。** 実装（機構があるか）、効果（実測の裏付けがあるか）、宣伝との整合（主張の強さが見合っているか）、独自価値（素のモデルや数行の指示で代わりになるか）、確信度。「機構はある・効果は未検証・宣伝は誇張気味」のように同時に成り立つ判定を、1つのラベルに押し込めない。集計表も自動で出る。
- **発火と能力は別の実験にする。** 能力実験では C 群のスキルを `/<name>` で強制的に読み込ませ、中身そのものの効果を測る。読み込まれなかった試行は主比較から外す。発火実験では、スキルを置いただけの状態で「使うべき依頼」と「使うべきでない依頼」を投げ、自動選択されるかを測る。
- **根拠の種類を必ず書く。** 実装確認済み / 推論による仮説 / 実験で観測 / 未確認 の4種。
- **再現できるようにする。** commit SHA、ファイルの fingerprint、監査モデル、日付を記録する。実験では計画を凍結（sha256）し、モデル ID・CLI バージョン・乱数シードを残す。

## 対照実験（Phase 2）

`claude -p` を試行ごとに別プロセス・別作業ディレクトリで動かす。オプションは `--setting-sources project --strict-mcp-config --no-session-persistence`。このため、利用者の CLAUDE.md・個人スキル・フック・MCP は読み込まれない。試行順はシードつきでランダム化する。採点は条件名とスキル名を伏せたうえで、別プロセスの LLM 審査員（ツールなし・構造化出力）か人手で行う。集計では平均・中央値・標準偏差、ブートストラップ 95% CI、n<5 の警告、時間・トークン・費用、スキルの読み込み率を出す。手順の詳細は [references/experiment-design.md](references/experiment-design.md) を参照。

### 必要なもの

- Claude Code CLI（`claude`。2.1.302 で検証）
- 対象スキルが C 群でスクリプトを実行しうるので、Claude Code の Bash サンドボックスが必要: `bubblewrap` と `socat`（Linux / WSL2）。`experiment.py selftest` が、ホームが読めないこと・ネットワークに出られないこと・作業ディレクトリ外に書けないことを実機で確かめる。通らない環境では、Bash を使う実験やスクリプトを含むスキルの実験を拒否する。

## テスト

```bash
python3 -m unittest discover -s tests -t .            # ユニットテスト（モデル呼び出しなし）
SLOP_LIVE=1 python3 -m unittest tests.live.test_live_acceptance -v   # 実エージェントでの受け入れテスト（有料）
```

受け入れテストでは、別プロセスのエージェントがこのスキルを使ってフィクスチャを監査し、その結果について次を検査する。

- 注入された指示に従わない
- 欠落した機能を「実装済み」と評価しない
- 外部 MCP の能力をモデルやスキルの能力と取り違えない
- データのない定量的な主張を「支持された」と判定しない
- 「代替可能」の判断が仮説のまま扱われている
- 実験していないのに数値を出さない
- 同じスキルを再監査したとき、引用するファイルが大きく変わらない

フィクスチャと期待される結論は [tests/fixtures/README.md](tests/fixtures/README.md) にある。`tests/test_self_audit.py` は、このスキル自身を棚卸し・監査したサンプルに対して、自分に甘い評価をしていないかを検査する。

## インストール前レビューへの組み込み（Phase 3・未実装）

インストーラやフックからは、一時領域に対して `fetch_target.py` → `inventory.py` → エージェントによる静的監査 → `report.py check` の順に呼べばよい。機械可読な出力は `audit.json` の `conclusion.verdicts`、`claims[].assessment`、`security_notes` と、`inventory.json` の `injection_candidates`・`missing_references`。インストールは利用者が結果を見て承認してから、監査とは別の手順で行う。監査の流れの中で対象のインストールコマンドは実行しない。

## 既知の制約と残課題

- 静的監査の質は監査するモデルに依存する。同じ版を再監査したときの安定性は、引用したファイルの一致度（`report.py diff`）で測れるが、判定ラベルまで同じになる保証はない。
- `inventory.py` の参照抽出と外部能力・注入候補の検出は、正規表現による手がかりにすぎない。見逃しも誤検出もある。判定には使わず、精読の入口として使う。
- 実験のバックエンドは Claude Code CLI だけ。Codex はスキルの置き場所（`~/.codex/skills`）と認証をユーザー環境から切り離す方法が未検証なので、まだ対応していない。
- エージェント CLI 自体は API と通信するため、プロセス全体のネットワークは遮断できない。隔離は Bash サンドボックスとファイルツールの許可ルールによるもので、完全ではない。不審な指示を含むスキルは実験しないことを推奨する。
- ブラインド化はスキル名などの文字列を伏せるだけ。出力の書式から条件が推測できる場合がある。
- 少数試行の結果は傾向にすぎない。結果はモデル・CLI・時点に依存するので、別のモデルに一般化しない。
