# READMEの宣伝と実装の照合

README・配布ページ・SKILL.md・ユーザー提供文書に含まれる**性能・効果の主張**を、検証可能な単位に分解して実装と照合する。

## 1. 抽出

- 対象: README（スキル直下とリポジトリ直下 `@repo/`）、SKILL.md の description と本文の効果記述、`@docs/` の提供文書。
- 主張は原文を短く引用し、位置（`path:行`）を付ける。言い換えだけで済ませない。
- 機能の一覧（「CSVをプロファイルする」）と効果の主張（「分析が正確になる」）を分ける。前者は実装照合、後者は効果の検証が要る。
- 曖昧な宣伝は、検証可能な形に分解する。例:
  - 「文章が自然になる」→「(a) 文法上の誤りが減る (b) 不要な修正をしない (c) 文体が統一される」のどれを主張しているか。READMEから読み取れなければ「どれとも特定できない」と書く。
  - 「バグが73%減る」→ 対象・比較条件・測定方法・データの有無。
  - 「導入するだけで自動的に」→ 起動条件（description）で本当に自動選択されるか、前提条件（外部ツール・キー）はないか。
- 同じ主張の繰り返しはまとめる。主要な主張に絞る（目安3〜10件）。

## 2. 各主張で検討すること

1. 主張されている効果は何か（`claimed_effect`）
2. それを実現するとされる仕組みは何か（`mechanism`。READMEが仕組みを説明していなければ「説明なし」）
3. 対応する実装は存在するか（`implementation_evidence` に位置）
4. 説明された動作と実装は一致するか
5. 実装があるだけで効果が成立すると言えるか（たいていは言えない。指示があることと、モデルがそれで良い結果を出すことは別）
6. 比較実験や測定結果が公開されているか（リポジトリ内にデータ・手法・再現手順があるか。「ベンチマークした」と書いてあるだけでは公開ではない）
7. 前提条件や制約（対応モデル、外部ツール、APIキー、言語、規模）が説明されているか

## 3. 判定（複数軸）

1つの主張に対して、互いに独立した5つの軸で判定する（`assessment`）。「機構は実装されている」「効果は未検証」「宣伝は誇張気味」は同時に成り立つので、1つのラベルに押し込めない。

| 軸 | id | 値 | 判定の問い |
|---|---|---|---|
| 実装 | `implementation` | `confirmed` 確認済み / `partial` 一部のみ / `missing` 欠落 / `contradicted` 説明と矛盾 / `not_applicable` 該当なし / `unknown` 不明 | 主張された**機構**はコードや指示として存在するか |
| 効果 | `effect` | `experimentally_supported` 実験で支持 / `not_supported_in_experiment` 実験で支持されず / `unverified` 未検証 / `not_assessable` 評価不能 | 主張された**効果**に実測の裏付けがあるか |
| 宣伝との整合 | `consistency` | `consistent` 整合 / `possibly_exaggerated` 誇張の疑い / `inconsistent` 不一致 / `not_assessable` 評価不能 | 主張の強さは、実装と根拠に見合っているか |
| 独自価値 | `unique_value` | 実装監査と同じ語彙: `base_model` / `short_instruction` / `unique_value` / `external_capability` / `undetermined` | その効果はスキルなしで（素のモデルや数行の指示で）得られそうか |
| 確信度 | `confidence` | `high` / `medium` / `low` | この主張についての判定全体の確からしさ |

`unique_value_basis` に独自価値の判断の根拠の種類（`implementation_confirmed` / `inference` / `experiment_observed` / `unconfirmed`）を書く。実験なしの独自価値判断はふつう `inference`。

軸ごとのルール:

- **実装**: `missing` は、欠落した部分を参照している行を `implementation_evidence` に示す。存在しないものを「確認済み」にしない。
- **効果**: `experimentally_supported` / `not_supported_in_experiment` には、この監査の実験（`experiment_ref`）か、手法とデータが追える公開資料の位置（`experimental_evidence_locations`）が必要。「ベンチマーク済み」と書いてあるだけでは `unverified`。
- **効果が `unverified` であることは虚偽を意味しない**。整合の軸を自動的に悪くしない。
- **宣伝との整合**:
  - `consistent`: 主張の強さが実装と根拠に見合う（例: 「CSVの統計を出す」と書いてあり、実際にそのスクリプトがある）。効果が未検証でも、主張が控えめなら整合でよい。
  - `possibly_exaggerated`: 実装や根拠に比べて主張が明らかに強い。定量値（「73%減」）に根拠がない、「劇的」「人間レベル」など。主張と根拠のギャップを `notes` に具体的に書く。
  - `inconsistent`: 明確な矛盾（宣伝された機能のファイルがない、動作が違う、実験で逆の結果）。「虚偽」と言えるのはこの場合だけ。
- **確信度**: 実装の軸は読めば確かめられるので高くなりやすい。独自価値や効果の判断が推論だけなら、ふつう `medium` 以下。
- 外部の記事・SNS・Stars数は根拠に数えない。

例: 「コードレビューの漏れが73%減る」という主張で、チェックリストはあるがデータがない場合 → 実装 `confirmed`（チェックリスト）、効果 `unverified`、整合 `possibly_exaggerated`（定量値に根拠なし）、独自価値 `short_instruction`（一般的なチェック項目のみ、`inference`）、確信度 `medium`。

## 4. 実験候補の選び方

実験未実施のときは、`experiments.recommended` に検証価値の高い主張を挙げる。優先度:

1. 導入判断に直結する効果の主張（「品質が上がる」「漏れが減る」）
2. B群（最小指示）との差が争点になる主張（スキル固有の価値の有無）
3. 定量的な主張（実験で検証しやすい）

各候補に、仮説と、効果が出るはずのタスクの案を一行で添える。
