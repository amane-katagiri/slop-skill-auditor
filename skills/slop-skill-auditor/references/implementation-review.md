# 実装・機能の監査と必要性の評価

対象スキルの説明を要約するのではなく、エージェントが実際に受け取る指示と、実際に動くコードを突き止める。

## 1. 何を明らかにするか

以下を、根拠の位置（`path:行`）付きで埋める。根拠を示せない項目は「未確認」とする。

| 観点 | 見る場所 | 注意 |
|---|---|---|
| 起動・選択条件 | frontmatter の `description`、`disable-model-invocation`、`user-invocable`、`paths`、`when_to_use` など | 発火条件はdescription頼み。広すぎる・狭すぎる記述は運用上の問題として記録 |
| モデルへの追加指示 | SKILL.md本文、そこから読ませる references | 「何をさせるか」を具体的に。抽象的な心構えだけなら そう書く |
| ワークフロー | 手順・チェックリスト・分岐条件 | 強制（必ず〜）か推奨か |
| 読む・生成/変更するファイル | 本文の指示、スクリプトの入出力 | |
| 呼び出すスクリプト・外部プログラム | 本文中のコマンド、`inventory.json` の `cli_command` / `subprocess` | スクリプトが**本当にあるか**、引数が合っているか |
| 外部能力（MCP / API / CLI / 検索） | `mcp_tool` / `network_code` / `env_var` / `url` | 外部サービスが実際に担う処理を書く。スキルに同梱されていない能力は「スキルの能力」ではない |
| 独自アルゴリズム・ルール | スクリプト本体、references の決定表 | 計算・解析が実装されているか、説明だけか |
| 固定テンプレート・参考資料 | assets、templates、references | 渡しているだけか、使い方まで規定しているか |
| モデルの推論に委ねる処理 | 「判断して」「適切に」等で丸投げされている箇所 | 中核がここにあるなら、価値の大部分はモデル由来 |

`inventory.json` の手がかりは網羅的でも正確でもない。手がかりがない箇所も読む。手がかりがあっても実際には使われていない場合がある。

### 外部能力の扱い

- C群（スキル適用）の成果が外部MCP・APIによるものなら、それは「モデルへの指示の改善」ではなく「能力の追加」。区別して書く。
- MCPサーバーやAPIキーがスキルに同梱されていない場合、利用者が別途用意する前提条件として書く。READMEがその前提を説明しているかも見る。
- 外部能力の品質（APIの精度など）は監査範囲外。分からなければ「未確認」。

### 欠落・不一致

- 参照されているのに存在しないファイル（`missing_references`）が担うはずの機能は**実装済みと評価しない**。
- どこからも参照されないファイル（`unreferenced_files`）は、エージェントが読まない可能性が高い。存在しても効果は期待しにくい、と書く（ただし人間向けの資料なら問題ない）。
- 本文の説明とスクリプトの実際の動作が違う場合は、両方の位置を示して記録する。

## 2. 機能の分解

主要な機能ごとに、次の分類を1つ以上つける（`categories`）。

| id | 分類 | 典型例 |
|---|---|---|
| `instruction` | 指示 | 「簡潔に」「〜に注意」「〜してはいけない」 |
| `knowledge` | 知識 | ドメインのルール、API仕様、社内規約、用語集 |
| `procedure` | 手順 | 処理順序、確認工程、チェックリスト、分岐 |
| `tool` | ツール | 同梱スクリプト、MCP、API、CLIへの接続 |
| `algorithm` | アルゴリズム | 具体的な計算・解析・変換のコード |
| `environment` | 環境 | モデル単体ではアクセスできない情報・実行環境・認証済み接続 |

各機能について、実際の処理、実装場所、使う外部能力、期待される効果を書く。機能の粒度は「それを外したらスキルの成果が変わる単位」。見出しの数に合わせて細切れにしない。

## 3. 必要性と独自価値

### 3.1 モデル内在能力との重複

問いは「このスキルなしで、同じ成果が同じ確度で出るか」。

- 一般知識・一般的推論で足りる内容か（例: 「わかりやすいコミットメッセージを書く」）
- 明示しないとモデルがやらない処理か（例: 特定の順序での確認、特定形式での出力）
- 長い指示は数行に縮められるか
- 書かれたノウハウはモデルが既に知っている一般論か、それとも固有の情報（社内規約、特殊なAPI、最新仕様、独自データ）か

「モデルは知っているはず」は**推論による仮説**として書く（`basis: inference`）。自分（監査エージェント）がその知識を持っていることは、別モデル・別設定での再現を保証しない。

### 3.2 独自価値として数えるもの

モデルが理論上できる処理でも、次の改善があれば価値として認める。

- 手順漏れの削減、確認工程の強制
- 結果の再現性・出力形式の安定
- 専門情報・独自データ・最新情報へのアクセス
- 決定的な処理の保証（計算・変換・検証をコードで行う）
- 毎回同じ指示を書く人間の負担軽減
- ツールの適切な利用（どの場面でどのツールを使うか）
- 実行時間・トークン・費用の削減（逆に増やしている場合も記録。`inventory.json` の `context_cost` は、起動時に読み込まれる SKILL.md と、そこから辿れるファイルのトークン数の概算。description が広すぎて関係ない依頼でも本文が読み込まれるなら、そのコストも書く）
- モデルの知識にない独自実装

逆方向の問題も記録する。決定的に書ける処理（計算、形式変換、検証）をモデルの推論に丸投げしている部分は、スクリプトにすれば再現性が上がる。これは `necessity.redundant` ではなく `open_questions` か `rationale` に「コード化の余地」として書く。

「長い」「網羅的」「専門用語が多い」は価値の証拠ではない。指示が長いほどコンテキストを消費し、他の指示と衝突する可能性もある。

### 3.3 置き換え可能性ラベル（`substitutability`）

| id | ラベル | 付ける条件 |
|---|---|---|
| `base_model` | モデル標準能力で代替可能と考えられる | 指示がなくても一般的なエージェントが通常そうする、または一般常識の範囲 |
| `short_instruction` | 短い追加指示で代替可能と考えられる | 1〜3行の自然な依頼で同じ挙動を引き出せそう、固有情報を含まない |
| `unique_value` | 独自の知識・手順・実装が価値を持つ | 固有の情報、決定的なコード、モデルが自発的にはしない検証手順など |
| `external_capability` | 外部能力が必要 | MCP・API・認証・特定環境がないと成立しない |
| `undetermined` | 現時点では判断不能 | 資料不足、外部依存の中身が見えない、など |

これらはすべて**暫定評価**。安易に `base_model` を付けない。迷ったら理由を書いて `short_instruction` か `undetermined` にし、実験候補に挙げる。

### 3.4 最小指示案（B群にそのまま使う）

最小指示案は「**READMEとdescriptionに書かれた目的を、普通のユーザーが数行で頼んだもの**」と定義する。監査者の知恵で強化してはいけない。スキル本文を熟読してから良い部分だけを数行に圧縮すると、それは「最適化した別のスキル」になり、B群との比較が意味を失う。

作り方:

1. **SKILL.mdの本文・references・スクリプトを読む前に**、README（スキル直下・`@repo/`）、ユーザー提供文書（`@docs/`）、SKILL.md の frontmatter（`description`）だけを読んで書く。
2. 書けるのは、そこに書かれた目的と、期待する成果物の形、普通のユーザーが自然に言いそうな一言だけ。目安3〜5行、多くても約400字（600字を超えると `report.py check` が警告する）。
3. 使った行を `derived_from` に記録する（`report.py check` は README・`@docs/`・frontmatter以外の位置をエラーにする）。
4. 書いた後で本文を読んで新しい発見があっても、**最小指示案は書き直さない**。気づいたことは `dropped` と `necessity` に書く。READMEに目的がほとんど書かれていない場合も、その乏しい情報から書く（それ自体が所見になる）。
5. 本文を読み終えたら `dropped` に「この最小指示では再現できないもの」（固有知識、決定的な処理、外部能力、特定の手順）を列挙する。これがスキル固有の価値の候補になる。

実験では `experiment.py init --audit-dir` がこの文をそのままB群に使い、凍結する。

自己監査（このスキル自身や、監査者がすでに本文を読んでいるスキル）では「本文を読む前に書く」が守れない。その場合は `limitations` に明記し、可能なら README と description だけを渡した別のエージェントに最小指示案を書かせる。

## 4. 根拠の種類（`basis`）

| id | 意味 | 例 |
|---|---|---|
| `implementation_confirmed` | ソースや設定で確認した事実 | 「`scripts/<name>.py:20-48` がCSVの列ごとの統計を計算する」 |
| `inference` | 実装から合理的に推定した仮説 | 「この程度の指示はモデル標準でも従うと考えられる」 |
| `experiment_observed` | 独立試行で観測した結果 | 実験結果ファイルに裏付けがある場合のみ |
| `unconfirmed` | 資料・測定不足 | 外部APIの挙動、未同梱のMCPサーバー |

「モデル標準能力で代替可能」「スキルによる品質改善」「READMEの性能主張が妥当」の3種の判断では、この区別を特に厳密にする。

## 5. 再監査の安定性

同じ版を再監査したときに、主要機能の抽出と実装位置が大きく変わらないことが望ましい。そのため:

- 機能は「ユーザーから見える成果の単位」で切り、位置は実際にその処理がある行範囲を示す。
- `inventory.json` の `fingerprint` と `provenance.json` の `commit` を必ずレポートに残す。
