# 対照実験の設計・実行・解釈

ユーザーが希望または明示的に許可した場合だけ行う。実験しなくても静的監査レポートは完結する。

## 1. 実験の種類と条件

スキルが**自動で選ばれるか**と、**使われたときに成果が良くなるか**は別の問いなので、別の実験として設計・報告する（`plan.json` の `experiment_type`）。

### 能力実験（`capability`、既定）

| 条件 | スキル | 追加指示 | 意味 |
|---|---|---|---|
| A Baseline | なし | なし | ユーザーが普段どおり頼んだ場合 |
| B Minimal Prompt | なし | Phase 1 で固定した最小指示案（`audit.json` の `minimal_prompt.text`） | READMEの目的を普通のユーザーが数行で伝えた場合 |
| C Full Skill | `.claude/skills/<name>/` に丸ごと配置し、**強制適用** | なし | スキルの中身が確実に使われた場合 |

- B群の指示は `init --audit-dir <audit_dir>` で `audit.json` からそのままコピーされ、凍結される。実験のために書き直さない。最小指示案はREADMEとdescriptionだけから作ったもの（implementation-review.md §3.4）。監査者が本文を読んで良い部分を圧縮した指示をB群に使うと、「最適化した別のスキル」との比較になってしまう。
- C群は `/<name> <タスク>` で強制適用し、ストリーム上の読み込みの証跡（`<command-name>/<name></command-name>`）で確認する。読み込まれなかった試行は主比較から除外され、`c_not_loaded` として別に報告される。
- C だけが外部ツール（MCP・API）を使う場合、差が「指示の改善」か「能力の追加」か区別できない。必要なら全条件に同じツールを与える補助実験を組む（`backend.mcp_config` と `mcp_config_conditions`）。

### 発火実験（`activation`）

- 条件はC（スキルを置いただけ、明示的な呼び出しやヒントなし）のみ。
- タスクに `should_activate: true / false` を付ける。使うべき現実的な依頼と、似ているが使うべきでない依頼（near-miss）の両方を入れる。
- 指標は依頼ごとの発火率と、全体の真陽性率・偽陽性率（件数つき）。品質の採点はしない。
- 発火しにくいスキルは「導入するだけで自動的に」という宣伝との整合に関わる。能力実験の結果とは混ぜずに報告する。

## 2. 手順

```
# audit_dir が一時ディレクトリにあるなら、ここより前にユーザーと決めた恒久的な場所へ移しておく
python3 -I <skill>/scripts/experiment.py init <audit_dir>/experiments/<exp_id> --skill-dir <skill_root> --audit-dir <audit_dir>
# plan.json を編集（下の設計原則）
python3 -I <skill>/scripts/experiment.py validate <exp_dir>
python3 -I <skill>/scripts/experiment.py selftest <exp_dir>     # サンドボックスの自己テスト
python3 -I <skill>/scripts/experiment.py run <exp_dir> --dry-run
# 試行数・モデル・概算費用をユーザーに示して承認を得る
python3 -I <skill>/scripts/experiment.py freeze <exp_dir>
python3 -I <skill>/scripts/experiment.py run <exp_dir>
python3 -I <skill>/scripts/experiment.py blind <exp_dir>
python3 -I <skill>/scripts/experiment.py grade <exp_dir>
python3 -I <skill>/scripts/experiment.py aggregate <exp_dir>
```

`run` は再開可能（完了済みの試行は飛ばす）。`freeze` 後に `plan.json` を変えると以降のコマンドは中止する。設計を変えたいなら新しい `<exp_id>` で作り直し、元の実験も報告に残す。

## 3. 設計原則

- **仮説から作る**: READMEの主要な主張（`claims[].id`）ごとに、反証可能な仮説を立てる。例: 「Cは A より、意味を変えずに文法誤りを多く直す」。
- **タスク**: 現実的なタスクにする。少なくとも
  - 一般タスク（普段の使い方）1つ以上
  - 宣伝された特徴が効果を発揮するはずのタスク1つ以上
  を含める。スキルが想定外の入力に過剰反応しないかを見る対照タスクもあるとよい。
- **評価指標は凍結前に固定**。ルーブリックは成果の品質を測る。**スキル自身が指示している手順を守ったか（例: 「指定の見出しを使ったか」）を性能の指標にしない**。それは「指示に従った」ことの確認にすぎない。
  - 文章改善系: 文法上の問題の修正、自然さ、意味の保持、不必要な修正の少なさ、文体の一貫性
  - コードレビュー系: 実在する問題の発見数（仕込んだ既知の問題で測る）、誤検出、修正の妥当性、テストの成否
  - 可能なら決定的なチェック（`checks`: テスト実行、出力の検証スクリプト）を使う。チェックはネットワークなしのbwrap内で実行される。
- **タスク文に採点基準や仮説を書かない**。実行エージェントには通常の依頼文だけを渡す。
- **同一条件**: モデル・effort・ツール・初期ファイルは全条件で同じ。違いは表の「スキル」と「追加指示」だけ。
- **試行数**: 各条件3回は「傾向を見る」最小限。差を主張したいなら5回以上。費用と相談する。
- **「差なし」の幅**: `analysis.neutral_band` を凍結前に決める。小さな差を事後的に「改善」と呼ばないため。
- **審査員に見せるファイル**: C群は中間ファイル（取得したソースのコピーなど）を大量に作りがち。成果物のファイルが決まっているタスクでは `grading_files` で審査員に見せるファイルを絞る（条件の推測を防ぎ、審査員の入力を揃える）。
- **独立性**: 各試行は別プロセス・別作業ディレクトリ・セッション保存なしで実行される（`claude -p --setting-sources project --strict-mcp-config --no-session-persistence`）。ユーザーのCLAUDE.md・個人スキル・フック・MCPは読み込まれない。組み込みスキルは全条件に同じく存在する。
- **ブラインド評価**: `blind` が条件名を隠し、スキル名・`SKILL.md`・`.claude/skills` の文字列を伏せる。ただし出力の書式そのものから条件が推測できる場合がある（限界として報告）。
- **採点**: 審査員にはタスク文・ルーブリック・入力ファイル（全条件で同一）・出力・差分だけを見せる。既定は別プロセスのLLM審査員（ツールなし、構造化出力）。審査員モデルは実行モデルと別にするのが望ましい。重要な判断には人手採点（`grading.mode: manual`）か複数回の審査（`judge_runs`）を使う。

### 3.1 手を抜いた出力で点が取れないか（凍結前に必ず確認）

ルーブリックは「良い出力」と「何もしない・手を抜いた出力」を区別できなければならない。凍結前に、そのタスクで**手を抜いた出力ならこのルーブリックで何点取れるか**を考える。何が「手抜き」かは分野によって違うので、監査者がタスクごとに決める。

| スキルの種類 | 手を抜いた出力の例（`reference_outputs`） |
|---|---|
| 文章の推敲・変換 | 入力をそのまま出力する no-op（`kind: copy`） |
| コードレビュー・検査 | 「問題は見つかりませんでした」だけの回答、一般論だけのチェックリスト（`kind: files`） |
| コード修正 | 何も変更しない、テストだけ通すように書き換える |
| ワークフロー・手順系 | 確認の質問を返すだけ、手順を説明するだけで実行しない |
| 調査・要約 | 入力の冒頭を切り出しただけの要約 |

- 作れるものは `tasks[].reference_outputs` に定義する。モデルを呼ばずに決定的に作られ、A/B/C と混ぜてブラインド採点される。条件ではなく参照行として報告され、どれかの条件と同点以上なら警告が出る。
- 意味のある手抜き出力が作れないタスク（例: 出力の形がまったく決まっていない対話）なら、`analysis.reference_note` にその理由を書く。
- 「壊さない」系の項目（意味の保持、余計なものを足さない、不要な変更をしない）は、何もしない出力が満点を取る。こうした項目を「直した」系の項目と同じ重みで合計しない。合計点とは別に、減点ゲート（一定以下なら失格）として読む。
- **直さないのが正解の対照タスク**（すでに自然な文、問題のないコード）は、スキルの過剰反応を見るためのもの。直すべきタスクと一緒に平均せず、別に報告する。

### 3.2 タスク固有の決定的指標

ルーブリックとは別に、決定的に計算できる数値を `tasks[].metrics` に定義できる。合計点には混ぜない。

- 変更量（例: `python3 -I $SLOP_TOOLS/text_metrics.py edit-ratio draft.md out.md`）。多いほど良いのか、少ないほど良いのか、参考値なのかは分野で違うので、`direction` を凍結前に宣言する。文章の推敲なら参考値（`informational`）が妥当なことが多い。
- 仕込んだ問題の修正数（例: フィクスチャに既知の不自然な表現を入れ、`text_metrics.py count-absent out.md <表現>...` で消えた数を数える）。「直すべき箇所」がはっきり定義できる分野でだけ使う。正解の表現が1つに決まらない問題は、決定的チェックではなくルーブリックで測る。
- 効果がそもそも数値で表せないスキル（ワークフローの整理など）には、無理に指標を作らない。

## 4. 安全

- 対象スキルのスクリプトがC群で実行されうる。`selftest` が、Claude Code の Bash サンドボックス（bubblewrap と socat が必要）が起動するか、ファイル系ツールが作業ディレクトリ外を読めないかを実機で確かめ、`selftest.json` に記録する。サンドボックスが使えない環境では、Bashを使うプランやスクリプトを含むスキルの `run` は拒否される。
- `--allow-unsandboxed` を付けると、Bash を全条件で**禁止**して実行する（サンドボックスなしの Bash は許可しない）。スクリプトの実行が価値の中心にあるスキルはこの条件では正しく測れないので、その旨を結果の限界に書く。ユーザーが理解したうえで求めた場合だけ使う。
- エージェントCLI自体はAPIと通信するため、プロセス全体のネットワーク遮断はできない。ファイル系ツールは許可ルールで作業ディレクトリ外を拒否している。完全な隔離ではないので、不審な指示を含むスキル（`security_notes` がある）は実験しないことを推奨する。
- 試行・selftest・審査員の起動にはすべて `disableAllHooks: true` を渡す。対象スキルのフロントマター `hooks:` やフィクスチャの `.claude/settings.json` のフックはサンドボックス外で動くため。`selftest` はフック付きのスキルとプロジェクト設定を置いて、フックが発火しないことも確かめる。フィクスチャと `files` 参照出力のディレクトリに `.claude/` や `CLAUDE.md` / `CLAUDE.local.md` があると `validate` が拒否し、起動直前にも作業ディレクトリを検査する（C群の `.claude/skills/<name>` だけはランナーが置く）。
- 試行は実験ディレクトリ・監査ディレクトリ・スキルの原本・他の `slop-*` 一時ディレクトリ・`/mnt` を読めず、書けない（許可ルールの Read/Edit/Write の deny とサンドボックスの denyRead・denyWrite。サンドボックスは既定で Claude の一時ディレクトリへの書き込みを許すため）。`selftest` はそこに置いた目印を読めないこと、実験ディレクトリと一時ディレクトリの兄弟ディレクトリに Bash と Write ツールで書けないこと（`write_isolation_ok`）を確かめ、どちらのモードもこれを満たさないと `run` は拒否される。`selftest.json` は Claude Code のバージョン・設定の形・`TMPDIR`・プラットフォーム・bwrap/socat の有無が一致し、中身が整合するときだけ再利用される。プランのパス（`skill.dir`、`fixture_dir`、`files` の `dir`、`mcp_config`）は監査ディレクトリ（`<audit_dir>/experiments/<id>` の場合）か実験ディレクトリの中になければならず、`~` は使えない。`init --skill-dir` も同じ。
- `claude` と審査員に渡す環境変数は許可リスト（PATH、HOME、ロケール、TMPDIR、プロキシ・証明書の設定など）だけ。`ANTHROPIC_API_KEY` などの認証用変数は `~/.claude/.credentials.json`（OAuth）が無いときだけ渡す。
- `backend.mcp_config` の MCP サーバーはサンドボックスの外で動くので、`run --allow-unsandboxed-mcp` を付けたときだけ実行し、結果の `isolation` に記録する。
- `checks` / `metrics` / 参照出力の `command` を動かす bwrap は、`/usr`・`/etc` などのシステムディレクトリと PATH 上の `python3` のプレフィックスだけを読み取り専用で見せ、`/tmp`・`/run`・`/var`・`/mnt`・`/home`・`$HOME` は空の tmpfs、作業ディレクトリだけ書き込み可にする。ネットワークなし、`--new-session`、全 capability を落とす。

## 5. 報告するもの

`aggregate` の `results.json` / `results.md` から:

- 各条件の成功率・ルーブリック得点（平均・中央値・標準偏差）
- 実行時間、トークン、費用（取れた分だけ。取れなければnullと理由）
- ばらつき、特徴的な成功例・失敗例（`trials/<id>/` を読んで具体的に）
- C>A か、C>B か、B と C の差が実用上重要か
- C群のスキル起動率
- READMEの宣伝効果が実証されたか（主張ごと）

集計が出す記述的なラベル（結論ではない）:

- 対ごと（C−A、C−B、B−A）の `label`: `better` / `worse` / `within_neutral_band` / `inconclusive`。`analysis.neutral_band`（ルーブリック合計点の「差なし」とみなす幅。凍結前に決める）と、ブートストラップ95%CIから決まる。どちらかの群が n<5 なら必ず `inconclusive`。
- `pareto_cost` / `pareto_tokens`: 品質差と費用差（またはトークン差）の組み合わせ。品質が上がって費用が下がる `PARETO_BETTER`、品質が上がるが高くつく `TRADEOFF_BETTER_COSTLIER`、品質は同等で安い `CHEAPER_SIMILAR` など。トークンはキャッシュ作成・キャッシュ読み取りも別に数える（スキル本文の読み込みコストが見えるように）。
- 決定的チェックがあるタスクでは、群ごとの成功率と Wilson 区間、Fisher の正確検定の p 値、そして `min_attainable_p`（この試行数で到達できる最小の p 値）。`min_attainable_p` が 0.05 より大きいなら、その試行数ではどんな結果が出ても差を主張できない。
- C群のスキル読み込み率、発火実験の真陽性率・偽陽性率にも Wilson 区間がつく。発火率が 0.5 ± 0.2 の依頼は `unstable` になる。

- 参照出力（手抜き出力）の行と `reference_flags`。参照出力がある条件と同点以上なら、その条件の「改善」はルーブリックが手抜きと区別できていない可能性がある。特に「壊さない」系の項目だけで勝っている改善は、単に変更が少ないことで説明できないか確かめる。
- タスク固有指標（`metrics`）の条件ごとの値と差。

`inconclusive` のときや信頼区間が0をまたぐときは、差を主張しない。「差は確認できなかった」と「差がないことが確認された」は別。

## 6. 解釈

結果を有効/無効の二値に還元しない。十分な試行と妥当な指標があるときの解釈の目安:

| 結果 | 解釈の目安 |
|---|---|
| A ≈ B ≈ C | 指示による品質改善は確認できない。ただし手間・一貫性・再現性の価値は残りうる |
| A < B ≈ C | 改善の主因は簡単な指示。スキル固有の追加効果は確認できない |
| A ≈ B < C | スキル固有の構成・知識・ツールによる改善の可能性 |
| A < B < C | 簡単な指示とスキル固有の構成の両方が寄与している可能性 |
| C < A または C < B | 悪影響・過剰な制約の可能性 |

品質とは別に、指示作成の手間、再現性（ばらつき）、運用負荷、速度、費用も評価する。

### 差の原因分析

C が優れていても「スキルが有効」で終わらせない。どの要素（特定の指示、references、スクリプト、外部ツール）が効いたかを考え、必要ならアブレーション実験（スキルのコピーから1要素を除いたものを別の `--skill-dir` で走らせる）を提案・実施する。効果が確認された要素と、確認されていない要素を分けて書く。

### モデル・時点への依存

結果には必ず、モデルID（`modelUsage` に出た実際のID）、effort、CLIとバージョン、利用可能ツール、スキルのcommit/fingerprint、実験日時、タスクと評価基準を記録する（`plan.lock.json` と `results.json` に入る）。ある時点・あるモデルで有効だったスキルが、別のモデルや将来も有効とは限らない。異なるモデルへ一般化しない。

## 7. audit.json への反映

- `experiments.status` を `"run"` にし、`experiments.runs` に `{id, results_file, summary}` を追加する（`results_file` は `<audit_dir>` 相対）。
- 実験で裏付けた主張は `assessment.effect: experimentally_supported`、`experiment_ref` に実験id。独自価値の判断も実験で更新したなら `unique_value_basis: experiment_observed`。
- 十分な試行で差が出なかった、または逆の結果が出た主張は `not_supported_in_experiment`。試行が少なく判断できないものは `unverified` のまま、`experimental_evidence` に「n回の試行で差を確認できず」と具体的に書く。
- 実験で `substitutability` の評価を更新した場合は `basis: experiment_observed` にする。
