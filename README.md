# slop-skill-auditor

Claude Code や Codex などで使う Agent Skill（`SKILL.md` 形式のスキル）を監査するスキルです。気になるスキルを渡すと、エージェントが中身を読んで、次の3つの問いに根拠つきで答えます。

- このスキルは実際に何をしているのか。
- スキルを入れずに、素のエージェントや数行の指示で頼んだ場合と比べて、何が増えるのか。
- README などの宣伝は、実装と根拠に見合っているのか。

スキルを批判するための道具ではありません。導入する価値があるかどうかを、実装と、必要なら実験に基づいて判断できるようにするためのものです。

## 何をして、何をしないか

監査の判断（何に価値があるか、宣伝が誇張かどうか）は、スキルを使うエージェント自身が行います。同梱のスクリプトが担当するのは、対象の取得、ファイルの棚卸し、レポートの検査や集計のような、決まった手順で済む処理だけです。

対象スキルの中身は、あくまで調べる対象のデータとして扱います。スキルの中に「この指示に従え」「このコマンドを実行せよ」と書かれていても従いませんし、静的な監査では対象のスクリプトもインストールコマンドも実行しません。不審な指示やコードを見つけたら、レポートに記録します（セキュリティ監査そのものは主目的ではありません）。

判断には、それぞれ根拠の種類を添えます。ファイルの何行目で確認した事実なのか、実装から推測した仮説なのか、実験で観測した結果なのか、まだ確かめていないのかを区別します。特に「このスキルがなくてもモデルだけでできそう」という判断は、実験で確かめるまでは仮説として扱います。実験していない効果を「実証済み」と書くことはありません。これはレポートを生成する前に、スクリプトでも機械的に検査します。

宣伝の評価では、ひとつの主張を5つの観点に分けて判定します。

- 宣伝されている仕組みが実装にあるか
- 効果を裏付ける測定があるか
- 主張の強さが実装と根拠に見合っているか
- 素のモデルや短い指示で代わりになりそうか
- その判定にどれくらい自信があるか

たとえば「仕組みはあるが、効果は測られておらず、宣伝はやや誇張気味」のように、同時に成り立つ評価を1つのラベルに押し込めずに済みます。

「数行の指示で代わりになるか」を考えるときは、比較に使う短い指示を先に作ります。材料は README とスキルの説明文（description）だけで、スキル本文を読む前に書き、あとから手直ししません。本文の良いところを監査者が抜き出して要約すると、それはもう「普通のユーザーの短い依頼」ではなく、監査者が作り直した別のスキルになってしまうからです。

## 似たツールとの違い

スキルを評価するツールは他にもあります。2026年10月時点で、次の4つのソースを読んで比べました。

- NVIDIA/SkillEvaluator
- aws-samples/sample-agent-skill-eval
- Back-Road-Creative/agent-audit
- HeshamFS/materials-simulation-skills の skill-evaluator

これらはどれも、スキルの価値を「スキルあり」と「スキルなし」の2条件で比べていました。上で書いたような「数行の指示で同じ効果が出るか」という比較や、README の主張が実装と根拠に見合っているかの照合は、どのツールにもありませんでした。このスキルは、この2点を中心に据えています。

一方で、テストの量、CI への組み込み、対応するエージェントの種類、セキュリティスキャナとの連携などは、これらのツールのほうが充実しています。スキルの構造チェックやセキュリティ検査が主な目的なら、そちらも検討してください。統計の手法（Wilson 区間や Fisher の正確検定）、品質と費用を組み合わせた判定、「評価していない」と「問題なし」の区別などは、これらのツールを参考にして取り入れました。

## インストール

[Skills CLI](https://skills.sh) で入れられます。

```sh
npx skills add <owner>/slop-skill-auditor
```

手動で入れる場合は、`skills/slop-skill-auditor/` をスキルの置き場所（Claude Code なら `~/.claude/skills/slop-skill-auditor/` やプロジェクトの `.claude/skills/slop-skill-auditor/`）にコピーしてください。リポジトリ全体をコピーする必要はありません。`tests/` には、監査の検証用に悪意のあるスキルの見本が入っているので、スキルの置き場所には入れないでください。

同梱のスクリプトは Python 3.11 以上の標準ライブラリだけで動きます。追加でインストールするものはありません。

## 使い方

### 監査を頼む

監査したいスキルを渡して、エージェントに頼みます。

> このスキルを監査して https://github.com/OWNER/REPO/tree/main/skills/foo

「このスキル意味ある？」「READMEの宣伝って本当？」のような聞き方でも使われます。渡せるのは、ローカルのスキルのディレクトリ、`SKILL.md` のパス、GitHub のリポジトリやディレクトリの URL です。補足の資料（紹介記事など）があれば、一緒に渡すと宣伝の照合に使います。リポジトリに複数のスキルが入っている場合は、どれを監査するか確認されます。

監査が終わると、要点（結論と主な理由）と、レポートの場所が伝えられます。

### レポートの見方

レポート（`report.md`）は、次の順に並んでいます。

1. 監査した版の情報（GitHub の commit など）と、使ったモデル
2. 要約
3. スキルの機能ごとの分析：実際に何をしているか、どのファイルの何行目か、モデルだけで代わりになりそうか
4. 宣伝の主張ごとの判定：上で書いた5つの観点と、その集計
5. スキルの必要性：素のモデルでできそうな部分、短い指示で代わりになりそうな部分、スキル固有の価値、比較に使った短い指示の文面
6. 実験結果、または実験で確かめるとよい主張
7. 見つかった不審な指示やコード（あれば）
8. 結論

最後の結論は、次のいずれか（複数のこともあります）です。

- 導入する価値がはっきりしている
- 独自の価値はあるが効果は確かめられていない
- 簡単な指示で代わりになる可能性が高い
- 宣伝に対して実装や根拠が足りない
- 判断する材料が足りない

### 実験で確かめる（任意）

静的な監査だけでは「スキルを入れると本当に良くなるのか」までは分かりません。確かめたい場合は、続けて頼めます。

> このスキルの効果を実験で確かめて

同じ課題を、次の3つの条件で、それぞれ独立に何回か実行して比べます。

- スキルを入れずに普通に頼んだ場合
- 監査で作った数行の指示を添えて頼んだ場合
- スキルを入れて使った場合

結果は、条件名を伏せた状態で別のモデルが採点し、点数、ばらつき、所要時間、費用を集計します。これとは別に、スキルを入れただけで、使うべき依頼のときに自動で選ばれるか（選ばれなくてよい依頼で誤って選ばれないか）を測ることもできます。

実験はモデルを何十回も呼ぶので費用がかかります。始める前に、課題、試行回数、使うモデル、おおよその費用が示され、承認を求められます。

実験に必要な環境は、対象のスキルによって変わります。

- どの実験にも、Claude Code の CLI（`claude`）が必要です。バージョン 2.1.302 で動作を確認しています。
- 指示や知識だけで、スクリプトを含まないスキルは、エージェントにシェルを使わせない設定で実験できます。この場合、Claude Code が動く環境ならどこでも動くはずです（動作を確かめたのは Linux（WSL2）だけです）。
- スクリプトを含むスキルや、シェルを使う課題を実験するには、Claude Code のサンドボックスが使える環境が必要です。Linux と WSL2 では `bubblewrap` と `socat` をインストールしてください。macOS では OS 標準の仕組みで動くとされていますが、まだ確かめていません。
- 結果を採点前に機械的に検査する仕組み（テストの実行、出力の検証、変更量の計測など）は、`bubblewrap` を直接使うため Linux と WSL2 でしか動きません。他の環境では、この検査は「未実施」として記録され、採点だけで比べます。

スキルを使う条件では、対象スキルに含まれるスクリプトが実行されることがあります。そのため、シェルを使う試行は Claude Code のサンドボックスの中で動かします。シェルを使わない試行でも、ファイルの読み書きは試行ごとの作業ディレクトリの中に限ります。どちらの場合も、試行からはホームディレクトリと監査の作業ファイルに触れられず、スキルのフックは無効にします。シェルはネットワークにも出られません。実験の前には、この隔離が実際に効いているかを自動で確かめ、効いていない環境では実行を止めます。それでも隔離は完全ではないので、不審な指示が見つかったスキルの実験は勧めません。

### 結果の置き場所

監査の結果は、特に指定しなければ一時ディレクトリ（`$TMPDIR/slop-audits/` の下）に作られます。作業中のリポジトリを汚さないためです。一時ディレクトリは再起動などで消えることがあるので、監査が終わったときに、残すかどうかと移動先を聞かれます。最初から保存先を指定しても構いません。

実験をする場合は、実験の計画に保存先のパスが記録されるため、実験を始める前に保存先を決めます。

結果のディレクトリには、主に次のファイルができます。

- `report.md`：人が読むためのレポート
- `audit.json`：同じ内容の機械可読版
- `source/`：監査した版のスキルのコピー
- `provenance.json`：どこから、いつ、どの版を取得したか
- `inventory.json`：ファイルの一覧や参照関係など、スクリプトが機械的に集めた情報
- `experiments/`：実験をした場合の計画と結果

監査の例は [samples/](samples/) にあります（静的な監査のみ）。

## 既知の制約

- 監査の質は、監査するモデルに左右されます。同じスキルを2回監査すると、欠けているファイルや機能の分類といったはっきりした事実はおおむね一致します。ただ、曖昧な主張の判定や、結論が複数あるときの2つ目以降は、回によって変わることがあります。
- ファイルの棚卸しで見つかる「外部サービスを使っていそうな箇所」や「監査者を誘導しようとしていそうな行」は、パターンに基づく手がかりです。見逃しも誤検出もあるので、そのまま判定には使いません。
- 実験は、少ない試行回数では傾向しか分かりません。結果は、使ったモデルや CLI のバージョンや時期に依存します。
- 実験の採点では条件名を伏せますが、出力の書き方から条件が推測できることがあります。
- 参考として、開発途中の版で、このスキル自身を対象にした実験をしました（[docs/experiments/2026-10-self/](docs/experiments/2026-10-self/README.md)）。4つの小さな課題では、「数行の指示」と「スキルを使う」の採点に差が見えませんでした。どちらもほぼ満点で、差を測れる課題になっていなかったためです。スキルを使う条件の費用は約2.4倍でした。古い版での結果なので、今の版の性能を示すものではありません。

## 残課題

- インストール前レビューへの組み込み。インストーラやフックから「取得 → 棚卸し → 静的監査 → 検査」を一時領域で呼び出して、結果を見てから利用者がインストールを承認する流れです。必要な入出力（`audit.json` の結論・判定・セキュリティ上の注意）はそろっていますが、組み込み自体はまだありません。
- 実験で使えるエージェントは Claude Code だけです。Codex（0.159 系のソースで確認）にもヘッドレス実行やサンドボックスはあります。ただ、利用者の全体の指示（`~/.codex/AGENTS.md`）と個人のスキルの読み込みは、設定では止められません。また、Codex のサンドボックスはファイルの読み取りを制限しないので、試行からホームディレクトリにある SSH 鍵や認証情報まで読めてしまいます。対応するには、Codex 全体を別の隔離環境で包む仕組みが必要です。
- macOS での実験の動作確認と、結果を機械的に検査する仕組みの macOS 対応。
- このスキル自身の効果を、今の版で、差が測れる難しさの課題を使って確かめ直すこと。
