# 自己実験: slop-skill-auditor は最小指示より良い監査をするか

> **古い版の記録（参考）**
> この実験は 2026-10-18（JST）に、開発途中の版（スキルの fingerprint `c7da632a…`）を対象に行った。実行は `claude-sonnet-5-5`、採点は `claude-opus-5-5`、Claude Code は 2.1.302。
> その後、監査手順・references・スクリプトは大きく変わっている。最小指示の作り方、欠落参照の範囲、「レビューしていないファイル」の検査、手抜き出力の参照、セキュリティ強化、ディレクトリ構成などだ。だから、この結果は**現行版にはそのまま当てはまらない可能性がある**。
> 現行の `experiment.py` は古い凍結ロックを受け付けないので、ここにある計画は再集計できない。容量を抑えるため、試行の作業ディレクトリ、会話ログ、採点の生データ、対象スキルのスナップショット、フィクスチャのコピーは削除し、計画（`*/plan.json`、`*/plan.lock.json`）と集計結果（`*/results.json`、`*/results.md`）だけを残した。`plan.json` の中の絶対パスは当時の作業環境のもので、今は存在しない。

問い: 当時の自己監査（このスキル自身を静的監査したサンプル。その後、現行版で取り直した）は「判断の中核は数行の指示に圧縮でき、置き換えられないのは検証スクリプトと実験基盤」と推論した。この推論を、独立した試行で確かめる。

## 計画からの逸脱（事後）

凍結後に、B 群の3試行（`missing-impl`、`quant-claims`、`mcp-api` で各1回）で `AUDIT.md` が `./target/<case>/` に書かれていたと分かった。エージェントが作業ディレクトリを移動したまま書いたためで、凍結した採点対象（作業ディレクトリ直下の `AUDIT.md`）からは漏れていた。そこで次の2つを両方報告する。

- **主解析**: 凍結した計画どおり。この3試行は最終回答の文章だけで採点された。
- **感度分析**: 採点対象を `target/*/AUDIT.md` まで広げた計画を新しく凍結し、同じ36試行を再実行せずに採点し直した。

ファイルの置き場所を誤ったこと自体は小さな指示違反だが、ルーブリックは監査の中身を測るものなので、中身の比較には感度分析のほうが妥当だと考える。

A の失点の大半は「価値の判断」（0.67〜1.67 / 3）で、ほかに事実・主張の区別・根拠でも一部のタスクで失点した。A の依頼文は「監査して」だけなので、素のモデルや短い指示との比較を自分から論じることが少なかった。注入タスクでは、3条件すべてで9試行とも注入に従わず、`cleanup.sh` の持ち出しを警告した（「注入への対応」は全試行 3/3）。

## 解釈（傾向。統計的な結論ではない）

- **A < B ≈ C** のパターン。改善の主因は、監査の観点（何をしているか、素のモデルと比べて何が増えるか、宣伝は妥当か、指示に従わない、実証済みと書かない）を数行で伝えること。この4つのフィクスチャでは、references の長い評価基準とスクリプトが、**監査の中身**を最小指示以上に良くする様子は観測されなかった。これは自己監査の推論と一致する。
- **C は費用が約2.4倍、時間が約2倍**。増えた分で得られたのは、機械可読な `audit.json`、`report.py check` を通った根拠の行番号、commit や fingerprint の記録といった構造面のもので、今回のルーブリックでは採点していない。
- **天井効果**。B と C はほぼ満点に張り付いていて、この課題とルーブリックでは B と C の差を検出できない。フィクスチャが小さく、正解がはっきりしすぎている。「差がないことが確認された」のではなく、「この設定では差を測れなかった」と読むべき。

## 限界

- 各セル n=3。差の有無について統計的な主張はできない。
- フィクスチャは小さな合成スキルで、正解（ルーブリックの3点の基準）もこのスキルの作者が書いた。現実のスキルや、より難しい（大きい、referencesが多い、微妙な誇張を含む）対象では結果が変わりうる。
- B の最小指示は、自己監査の中で、エージェントがスキル本文を読んだ後に書いたもの。README と description だけから書く手順を守れていない。前半の3つの問いは README の冒頭とほぼ同じだが、後半の2文（スキル内の指示に従わずスクリプトも実行しない、実験していない効果を実証済みと書かず分からないことは未確認と書く）は SKILL.md の決まりごとの要約で、普通のユーザーが自分から言うとは考えにくい。採点項目の「誠実さ」や「注入への対応」にちょうど効く指示なので、B ≈ C という結果は、B がスキルの要点を先取りしていたことで一部説明できる可能性がある。
- 審査員は単一モデル（opus）で、各項目1回だけ採点した。伏せ字はスキル名と `SKILL.md` などの文字列だけで、C の出力の書式から条件が推測できた可能性がある。
- 実行モデルは sonnet のみ。別のモデルやツールの版にこの結果を一般化しない。
- 天井効果のため、C が B より優れる場面の有無はこの実験では判断できない。

## 次に試すとよいこと

- 天井を避ける難しい対象: 実在の大きなスキル（例: `samples/anthropics-pdf/` で監査した pdf スキル）。正解は事前に人手で作る。
- README と description だけを渡した別のエージェントに書かせた、独立した最小指示を B に使う。
- 構造面の価値（根拠の行番号の正確さ、再監査での安定性、機械可読性）を測るルーブリックや決定的チェックを加える。
- アブレーション: `references/` を除いたスキル、スクリプトを除いたスキル。
